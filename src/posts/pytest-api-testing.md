# 给全栈项目写 pytest 接口测试：14 个用例全绿 + TDD 修掉 2 个真实 bug

> 一句话理解：接口测试就是「检查实际表现是否符合预期」——给自己的全栈项目（AI 热点选题助手）写了 14 个 pytest 用例，覆盖正常/边界/异常，顺手用 TDD 修了 2 个输入校验 bug，还学会了 mock 第三方 AI。

## 我之前的误解

- 以为「测试是测试工程师的事」——其实自己写的接口，行为最清楚，是最容易上手练测试的地方。
- 以为 mock 很复杂——其实 mock 就是「用假接待员代替第三方 AI」，返回写死的答案，不花钱、快、稳定，专心验证后端自己的逻辑。

## 用 TDD 修掉的 2 个真实 bug

**Bug 1：非法平台返回 503（应该 400）**
- 现象：`POST /api/topics` 传 `platform=xxx` → 返回 503「暂无热榜数据」
- 原因：后端只检查参数「存在」，没检查平台「合法」
- 修复：加 `if (!isValidPlatform(platform)) return 400`
- 过程：写测试（期望 400）→ 红（实际 503）→ 修 → 绿

**Bug 2：views 传非数字被静默改成 0**
- 现象：`POST /api/reviews` 传 `views="abc"` → 返回 200，views 悄悄变成 0
- 原因：`Number("abc") || 0` → NaN 被 `||` 兜底成 0
- 修复：`Number.isNaN(viewsNum)` 时返回 400「views 必须为数字」
- 过程：写测试（期望 400）→ 红（实际 200）→ 修 → 绿

## 核心概念（这次真正理解了的）

1. **测试的本质**：检查「实际表现」是否符合「预期」
2. **用例设计**：正常 / 边界 / 异常——从「输入」角度列情况，预期从接口规定推理（不靠猜）
3. **断言**：`assert 条件`，不对就报错变红
4. **红绿流程**：红 = 有问题，绿 = 没问题
5. **TDD**：先写测试（表达「应该怎样」）→ 红 → 修代码 → 重启后端 → 绿
6. **mock**：假数据替换第三方依赖，只验证自己的逻辑

## 踩过的坑（下次注意）

- **改后端代码必须重启**，否则测的是旧代码
- **端口被旧进程占用**：`netstat -ano | grep :3000` 找 PID → `Stop-Process -Id <PID> -Force`
- **测试创建的数据要清理**：用 DELETE 清理，避免污染真实数据
- **测第三方 API 先只测参数校验**（不花钱）；正常流程用 mock
